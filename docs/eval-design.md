# 评测设计：把“Harness 好不好”拆成可诊断的问题

## 1. 现在评的是什么

`模型 × Harness → 任务通过率` 是一个**混合指标**：通过了说不清是模型强还是 Harness 有用，失败了也找不到该改哪一块。
评测 Harness 的前提是**固定模型和任务，只改 Harness 的一个部件**，所以每个部件都要有自己的假设、指标和对照。

## 2. 部件 → 假设 → 对照 → 指标

| 部件 | 假设 | 对照实验（消融） | 主要指标 | 变差时去哪改 |
|---|---|---|---|---|
| 完成门禁 | 强制验证减少“未验证就交差” | 关闭门禁 | 通过率；`edit_without_final_verification` 占比 | 门禁条件、拒绝提示措辞 |
| 先读后写 | 先看仓库再改，减少改错位置 | 关闭前置检查 | 通过率；探索调用数；策略错误数 | `repo_overview` 返回内容 |
| 上下文压缩 | 省 token 且不降低效果 | 关闭压缩 / 更激进压缩 | 末步 prompt token；长任务通过率 | 保留与丢弃的规则 |
| 工具契约 | 工具参数与错误信息让模型能一次用对 | 放宽/收紧工具约束 | 工具失败率及其原因分布 | 工具 schema、报错文案、沙箱策略 |
| 运行限制 | 限制不误杀正常任务 | 放宽/收紧上限 | `budget_exhausted` 占比 | 默认限制值 |
| 错误反馈 | 具体报错帮助自我纠正 | 把报错换成泛化文案 | 失败后一步内修复比例 | 工具返回的错误内容 |

> 以上是**实验计划**，目前只有“工具契约”一行有真实数据（见 §4）。其余消融需要先给 Runtime 加开关，并且需要有区分度的任务（见 §5）。

## 3. 记录哪些过程指标（`benchmarks/analyze_runs.py`，只读事件日志）

- 结果层：评分通过率；运行是否正常结束。
- 轨迹层：改动前探索调用数；首次修改后的验证是否通过；最后一次修改后是否验证；是否审阅 diff；重复读同一文件次数。
- 工具层：工具失败率；失败按 `工具|错误类型|信息` 分布；策略错误数。
- 成本层：首步与末步 prompt token（上下文增长）。
- 失败归类（互斥）：`ok`、`env_error`、`env_error_after_fix`、`budget_exhausted`、`runtime_error`、`no_edit`、`edit_without_final_verification`、`verified_failing_but_stopped`、`visible_tests_pass_hidden_fail`。

“环境故障”单独归类，避免把网络错误算成模型或 Harness 的失败。

## 4. 已有数据能说明什么（deepseek-flash × repo-fix-v1 × 3 轮 = 42 次运行）

| 观察 | 数据 | 含义 |
|---|---|---|
| 评分通过率 | 42/42 | 套件对该模型饱和，不能区分部件好坏 |
| 门禁拒绝 / 策略错误 | 0 / 0 | 模型自觉遵守流程，门禁没有发挥机会 |
| 首次修改后验证通过 | 97.6% | 小任务上基本一次改对 |
| 重复读同一文件 | 平均 0.02 次/运行 | 上下文压缩未造成“忘了又读” |
| 末步 prompt token / 首步 | 约 3.3k / 1.0k | 短任务上下文增长温和，压缩几乎不触发 |
| 工具失败率 | 21/322 次调用 ≈ 6.5% | **可操作的发现，见下** |

**工具失败的构成（唯一有真实改进线索的部分）：**

- 16 次 `run_tests`：`PermissionError: Inline Python execution is not allowed`。模型想用 `python -c ...` 探查行为，被沙箱拒绝；占 `run_tests` 全部调用（67 次）的 24%，占全部工具失败的 76%。
- 4 次 `apply_patch`：`Each file may appear once per patch batch`，模型在同一批补丁里对同一文件提交了多处修改。
- 1 次 `apply_patch`：`old cannot be empty for replace operations`。

这些都被模型自行恢复，没有影响最终通过，但它们是**工具契约与沙箱策略与模型预期之间的摩擦**：
候选改进是（a）在工具描述里明确“不能内联执行，请用测试文件”，（b）允许同一文件在一批补丁里多处修改并按顺序应用。改完后用同一套任务复测“工具失败率”，就是一个可量化的、归因清晰的改进实验。

另外：2 次运行在修复写入之后遇到瞬时网络错误（`SSL: UNEXPECTED_EOF_WHILE_READING`），Planner 没有重试，运行被标为 failed 但评分通过（`env_error_after_fix`）。

## 5. 让评测有区分度所需的条件

当前任务线索过多（点名函数、有现成失败测试、文档字符串写明规格）、仓库很小、题型为经典算法题，所以强模型无压力。
目标是让主力模型通过率落在 30%–70%：去掉线索、去掉现成失败测试、增大仓库并加入干扰文件、使用非经典业务逻辑、把规格放进文档。
并用明显更弱的模型（本地小模型）做对照，若弱模型也接近满分则说明是任务过简单而非模型强。

## 6. 局限

- 单一模型、单一套件、14 个人工编写的小任务，不能外推到真实仓库（如 SWE-bench）。
- 未设置 temperature，使用服务默认值。
- 消融开关尚未实现，上表中除“工具契约”外的假设均未检验。
